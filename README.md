# Quiet Zone Monitor

An IoT-based sound monitoring and alert system that combines **audio-based machine learning, ESP32 hardware simulation, threshold-based alerting, and cloud visualization**.

The system analyzes real audio input using a locally running machine learning model, sends the resulting sound-level/prediction information to an ESP32, and activates an LED and buzzer when the sound level exceeds a predefined threshold. At the same time, the measured data is sent to **ThingSpeak** for storage and graphical visualization.

---

## Project Overview

The **Quiet Zone Monitor** is designed to monitor sound in an environment and identify when the sound level becomes significant enough to require an alert.

The project combines three main parts:

1. **Machine Learning System** – receives real audio and performs sound analysis/prediction.
2. **ESP32 IoT Hardware** – receives the prediction/sound-level value and controls the output devices.
3. **ThingSpeak Cloud Visualization** – stores the collected values and displays them as graphs for monitoring and comparison.

---

## Why Was This Project Built?

Traditional sound-level monitoring systems generally use a fixed threshold and simply detect whether sound is loud or quiet. This project introduces a machine-learning component to analyze the audio and provide a more intelligent sound-monitoring approach by finding whether it's a human sound or non-human sound.

The project was built to:

* Monitor audio/sound conditions in real time.
* Automatically trigger an LED and buzzer when the configured threshold is exceeded.
* Differentiate human and non-human sound.

## System Architecture

The project is divided into three major sections.

### A. Machine Learning Section

The ML system receives audio input and extracts numerical audio information/features required by the trained model.

The processed features are passed through the saved scaler and then to the trained SVC model.

```text
Audio Input
    │
    ▼
Audio Signal
    │
    ▼
Feature Extraction
    │
    ▼
scaler.pkl
    │
    ▼
SVC Model
    │
    ▼
Prediction / Sound-Level Value
```

### B. ESP32 Hardware Section

The ESP32 receives the value generated by the ML system.

It compares the received value with a predefined threshold.

```text
Prediction / Sound-Level Value
             │
             ▼
       ESP32 receives
             │
             ▼
      Compare with threshold
             │
       ┌─────┴─────┐
       │           │
    > Threshold  ≤ Threshold
       │           │
       ▼           ▼
 LED + Buzzer    No Alert
     ON
```

### C. Cloud Visualization Section

The monitoring data is also sent to ThingSpeak.

ThingSpeak is used for:

* Data storage
* Time-series visualization
* Graph generation
* Comparing sound-level values over time

The cloud is therefore primarily used as the **monitoring and visualization layer**, while the local ML system performs the sound analysis.

## Machine Learning Model

The project uses an **SVC (Support Vector Classifier)** for sound classification.

SVC is based on the Support Vector Machine (SVM) algorithm.

Its purpose is to find a suitable decision boundary between different classes in the training data.

In our project, the general ML pipeline is:

```text
Audio
  │
  ▼
Feature Extraction
  │
  ▼
Feature Scaling
  │
  ▼
SVC
  │
  ▼
Prediction
```

---

## Audio Processing

The system works with digital audio samples.

A microphone/audio recording provides a sequence of sample values representing the audio waveform.

```text
Sound
  ↓
Microphone
  ↓
Audio Signal
  ↓
Digital Samples
  ↓
Feature Extraction
  ↓
ML Model
```

### Sampling Rate

The sampling rate specifies how many audio samples are captured per second.

```text
16,000 Hz = 16,000 samples per second
```

### Recording Duration

The `duration` value determines how long each audio segment is recorded.

```text
duration = 2 seconds
```

## Threshold-Based Alert

After the ML/audio-processing stage, the resulting value is sent to the ESP32.

The ESP32 compares the received value against a predefined threshold.

Our project currently uses:

```text
Threshold = 0.02
```

The threshold is selected based on experimental observations of the values produced by the system under different sound conditions.
Our project uses a normalized amplitude/RMS-like value, so `0.02db` is a threshold in that numerical scale.

## Wokwi Hardware Simulation

The hardware portion of the project is simulated using **Wokwi**.
It can be viewed here: https://wokwi.com/projects/460472245718122497

The ESP32 simulation represents the IoT device that receives the ML output and controls the alert hardware.

### Simulated Hardware

* ESP32
* LED
* Buzzer
* 220 Ohm resistor
* Wi-Fi/network communication

### Hardware Work Flow

```text
ML Prediction
     │
     ▼
   ESP32
     │
     ▼
Threshold Comparison
     │
     ├───────────────┐
     │               │
 Above threshold   Normal
     │               │
     ▼               ▼
LED ON            LED OFF
Buzzer ON         Buzzer OFF
```

Wokwi allows the hardware behaviour to be tested without requiring the physical ESP32 and electronic components.

## ThingSpeak Visualization

ThingSpeak is used as the cloud monitoring platform.

The ESP32 sends monitoring data to ThingSpeak while the local system performs the sound analysis.

ThingSpeak stores the values and displays them using time-series graphs.

### Data Flow

```text
ML / ESP32
    │
    │ Data
    ▼
ThingSpeak
    │
    ├── Store data
    │
    └── Display graphs
```

# To Run the Machine Learning Model

Train the model if `.pkl` files are not created

```bash
python train_model.py
```

This step trains the classifier and saves the required objects in 

```text
scaler.pkl
human_sound_model.pkl
```

If the `.pkl` files have already been generated, retraining is not required for every prediction.

Run the prediction system

```bash
python main.py
```

The application:

1. Captures/receives audio.
2. Processes the audio.
3. Extracts the required features.
4. Loads the scaler.
5. Scales the features.
6. Loads the trained SVC model.
7. Generates the prediction.
8. Sends the required value to the ESP32.

---

# To Run the ESP32 Simulation in Wokwi

1. Open the project in Wokwi(https://wokwi.com/projects/460472245718122497).
2. Open the ESP32 simulation.
3. Verify the LED and buzzer connections.
4. Verify the Wi-Fi/network configuration.
5. Start the simulation.
6. Run the Python prediction application.
7. Allow the ML system and ESP32 simulation to communicate.
8. Observe the ESP32 output.

When the received value exceeds the configured threshold:

```text
LED → ON
Buzzer → ON
```

Otherwise:

```text
LED → OFF
Buzzer → OFF
```
